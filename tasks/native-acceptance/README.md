# 原生验收与故障回归

运行 `cargo run --release -p native-acceptance`。命令启动独立游戏副本，在 Unity 主线程调用真实的游戏放置动作和模拟器。它不会操作正在玩的存档。

正例是一座三层、12 带输入与 12 带输出的直通工厂。负例由同一蓝图派生；测试必须收到指定错误才通过，启动失败、编译错误和其他异常不能冒充预期失败。

| 用例 | 必须检测的问题 |
| --- | --- |
| healthy | 普通玩家完整放置，12 带额定吞吐，断料及堵塞后恢复 |
| upper-trash | 上层垃圾桶导致原生建筑载荷拒绝，留下空平台 |
| outside-floor | 建筑占地超出可建造地板 |
| half-speed | 每条带串联单个旋转器，吞吐降为半速 |
| wrong-shape | 产量正常，但输出错误形状 |
| latched-output | 正常生产后注入堵塞锁死，解除堵塞仍不能恢复 |
| no-experiment | 仅推进模拟时间，没有生产验收实验 |
| unverified | 实验返回观察数据，没有明确通过断言 |

`latched-output` 的故障在输出接收器注入，生产和积压仍由真实游戏模拟器执行。其余蓝图故障通过实际建筑载荷和供料触发。

## 放置与生产标准

宿主固定为普通经典场景，使用其完整科技树，准备足够蓝图货币。以 `LocalHost` 身份执行 `ActionModifyIsland` 及其嵌套的 `ActionModifyBuildings`，不开启强制放置或跳过检查。逐项核对平台/建筑数量、建筑定义、位置和朝向；原生岛屿动作返回成功但内部建筑为空也必须失败。需要裁剪的诊断实验先验证完整蓝图放置，再通过原生删除动作裁剪。

`ProductionAcceptance` 在同一个持续运行的世界内执行：

1. 预热 120 模拟秒，随后计量 120 秒。根据游戏当前传送带配置计算额定速率；每条输入实际接收量、每条输出产量都必须与额定值相差不超过一个物品，同时逐带检查完整形状编码。
2. 停料 120 秒排空，再观察 30 秒，要求无输出；恢复供料并计时验收。
3. 分别阻塞全部输出、交错输出、各独立输出组。堵塞 120 秒后计量 30 秒，被阻塞端不得接收物品；溢流设计的未堵塞输出仍须满速。
4. 每次恢复每 10 秒计量一次，120 秒内必须出现连续三个全带满速窗口；之后再持续满速运行 120 秒，同时核对输入接收量。恢复计时包含这三个确认窗口。

报告保存每条带的形状、产量、输入接收量、各扰动阶段和恢复时间。首次失败立即使套件返回非零，完整错误与采样数据留在运行目录的 `report.json`。

## 入口的验收含义

- `blueprint`：必须有明确返回 `verified: true` 的实验；没有断言不能通过。
- `place-blueprint`：只验收完整原生放置，报告 `scope: placement`，不声称吞吐合格。
- `blueprint-diagnostic`：容量测量、裁剪接入测试、定义导出等诊断，报告 `verified: null`、`scope: diagnostic`，终端显示 `DIAGNOSTIC`。旧 CMAM 的“输入需求全速”和“产出一个目标”属于这里。

生产单元实验可以声明低于整带速度的输入额定值，整座工厂默认每条输入满带。四分切割工厂和 weave、两种对角切割、溢流对角切割、三种优先合流共用这套扰动测试；优先级、合流器空接头、形状切换等任务特有断言仍保留。

## 实际工厂命令

```powershell
cargo run --release -p diagonal-cut
cargo run --release -p priority-merge
cargo run --release -p quarter-cut -- native <factory.spz2bp>
cargo run --release -p diagonal-cut -- overflow <output-directory/reference.spz2bp>
```

最后一条使用仓库内的溢流参考生成蓝图，并在验收通过后写入所给路径的同一目录。四分切割的构建需要任务文档中说明的 OR-Tools、SCIP 和 protoc 环境。

当前加严验收抓到的真实失败：既有 `quarter-cut-1x2-original` 能正常满速生产，但断料重启后的前 120 秒只出现两个连续全带合格窗口，未通过三窗口恢复要求。保留失败，不增加等待时间来让现有产线过关。
